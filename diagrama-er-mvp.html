Modelo entidad-relación del MVP

Consentimiento informado digital para la estética de mascotas. Este modelo mantiene el alcance inicial pequeño: un cliente registra una mascota y firma un consentimiento para esa mascota. Si trae tres mascotas, completa tres envíos.

Por qué están estas tablas

  • usuario: representa a la persona, sea cliente dueño (CLIENTE) o Pilar (ADMIN). El rol es un atributo: no se duplica la persona en una tabla de dueños y otra de administradores.
  • Acceso: solo Pilar inicia sesión en el MVP. El cliente se registra en el envío público, pero no recibe cuenta ni contraseña; contrasena_hash solo aplica al usuario administrador.
  • mascota: cada mascota apunta al usuario dueño. Un dueño puede registrar varias mascotas. Raza y edad aproximada pueden ser opcionales.
  • version_consentimiento: conserva el texto publicado que se presentó para firmar.
  • consentimiento: representa un envío firmado para una mascota. El cliente firmante se obtiene desde la mascota y su usuario dueño, evitando guardar dos referencias que pudieran apuntar a personas distintas.

Decisiones y límites del MVP

  • Una fila de consentimiento refiere a una sola mascota: si el cliente trae tres mascotas, firma tres envíos. No se necesita la tabla intermedia consentimiento_mascota.
  • La imagen de firma queda en el mismo envío; no se necesita una tabla firma aparte en esta versión.
  • El servidor asigna el rol CLIENTE en el formulario público; nunca debe aceptar que el visitante envíe su propio rol, estado de administrador o contraseña.
  • La API solo permite a una persona con rol ADMIN consultar registros. El formulario público no puede leer consentimientos existentes.
  • Teléfono y correo deben recopilarse solo si son necesarios. No se marcan únicos en el modelo porque una familia puede compartirlos; decidir cómo reconocer a un cliente recurrente antes de implementar historial.
  • Las versiones publicadas del texto no se editan: cualquier cambio crea una nueva versión. Así se identifica qué texto aceptó cada cliente.
  • La fecha y hora se asignan en el servidor; el formulario público se abre tanto con QR como desde la tablet.
  • No se incluyen número de documento, dirección IP, agente del navegador ni datos médicos: no son necesarios para el flujo descrito.
  • El consentimiento enviado no se edita ni se elimina desde la aplicación; una corrección requiere un nuevo envío, según la especificación.

Sustento y decisiones por confirmar

Una sola tabla usuario evita duplicar el concepto de persona: rol distingue cliente y administrador. El formulario crea un usuario cliente sin credenciales; Pilar tiene una cuenta protegida para iniciar sesión. La mascota apunta a su dueño y cada consentimiento apunta a la mascota y a la versión exacta del texto. Así el dueño firmante se obtiene siguiendo la relación, sin almacenar una relación redundante que pudiera contradecirla. En Nest.js, el servidor valida roles y datos; PostgreSQL los almacena y Prisma permite consultarlos.

Si una persona vuelve con varias mascotas, el modelo permite una persona con varias mascotas, pero el MVP aún debe decidir cómo reconocer que un formulario pertenece al mismo cliente sin crear duplicados. No conviene usar teléfono o correo como identificador único sin aprobar esa regla, porque pueden compartirse o no estar disponibles.

Antes de implementar, confirmar con el profesor si exige otros campos. Antes de usar datos reales, definir qué contacto es obligatorio y revisar con la institución o asesoría competente el aviso de privacidad, la conservación de datos y el texto legal del consentimiento. Este diagrama no es una validación legal.

Para proteger el historial, la aplicación debe tratar los consentimientos enviados y las versiones publicadas como inmutables. Si más adelante se necesita PDF, correo o WhatsApp, se puede añadir sin ampliar las tablas principales ahora.
